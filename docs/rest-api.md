# REST API Layer: Appointment Endpoints

A beginner-friendly walkthrough of the HTTP layer introduced in **Step 13**, which exposes
the appointment business logic to API clients.

---

## The Big Picture

```
HTTP request (JSON)
    ↓
AppointmentController    ← accepts DTOs, validates, picks the HTTP status
    ↓
AppointmentService       ← the single owner of business rules (Step 12)
    ↓
Spring Data repositories ← read/write rows
    ↓
MySQL (Flyway-owned schema)
```

New code added in this step:

```
com.medbook.controller
└── AppointmentController        ← POST/GET/CANCEL endpoints

com.medbook.dto
├── CreateAppointmentRequest     ← what a client may send to book
├── CancelAppointmentRequest     ← what a client may send to cancel
├── AppointmentResponse          ← what the server sends back
└── ErrorResponse                ← consistent shape for every failure

com.medbook.exception
└── GlobalExceptionHandler       ← exception -> ErrorResponse + status
```

One small service addition was required: `AppointmentService.getAppointment(id)`, a
read-only lookup used by `GET /api/v1/appointments/{id}` (backed by a fetch-join query,
`AppointmentRepository.findByIdWithPatientAndDoctor`, because Open Session In View is off
and the relationships are lazy). The booking and cancellation flows are unchanged.

---

## What Does a REST Controller Do?

A controller is a **translation layer** between HTTP and Java:

1. reads the HTTP request (JSON body, path variables),
2. validates that the request is structurally sound,
3. calls the service method that owns the business rule,
4. maps the result to a response DTO,
5. chooses the HTTP status code.

It decides **how the API speaks**, never **what the business rules are**. There is no
`if (doctor.isActive())`, no overlap query, and no `@Transactional` in the controller: all of
that belongs to the service, which works identically whether it is called from HTTP, a test,
or a future background job.

---

## Why DTOs Instead of JPA Entities?

The JPA entity (`Appointment`) is a *database* object. Returning it directly from a
controller would create several problems:

| Problem | Why it matters |
|---|---|
| **API contract couples to the schema** | Renaming a column would silently rename a JSON field and break every client. |
| **Lazy associations** | Jackson would try to serialize `patient` and `doctor`; both are `LAZY`, and with `spring.jpa.open-in-view=false` this fails with a `LazyInitializationException` outside the transaction. |
| **Client-writable internals** | Accepting the entity as input would let a client submit `status`, the fee snapshot, or the ID — all of which must stay server-controlled. |
| **Leaky internals** | An entity serializes whatever fields it happens to carry, including ones not meant for clients. |

So the API uses three small immutable records (Java 21 *record* classes):

- **request DTOs** describe exactly what a client may send,
- **response DTOs** describe exactly what the server promises to return.

The conversion is a single static method, `AppointmentResponse.from(Appointment)`, which reads
only plain columns and the participants' IDs — never a lazy association.

## Endpoints

| Method | Path | Purpose | Success status |
|---|---|---|---|
| `POST` | `/api/v1/appointments` | Book an appointment | **201 Created** (+ `Location` header) |
| `GET` | `/api/v1/appointments/{id}` | Read one appointment | **200 OK** |
| `POST` | `/api/v1/appointments/{id}/cancel` | Cancel an appointment | **200 OK** |

The existing `GET /api/v1/hello` is unchanged.

**Not implemented (on purpose):**

- `GET /api/v1/doctors/{id}/appointments` / `GET /api/v1/patients/{id}/appointments` —
  the service layer does not offer listing methods yet, so no endpoints were created for
  them (adding them is a future step together with the service methods).
- confirm/complete endpoints — the service does not implement those transitions yet.

## Request and Response Examples

### Book an appointment

```http
POST /api/v1/appointments
Content-Type: application/json

{
  "patientId": 12,
  "doctorId": 5,
  "appointmentDate": "2026-10-01",
  "startTime": "10:00",
  "endTime": "10:30"
}
```

`201 Created` — with `Location: /api/v1/appointments/41`:

```json
{
  "id": 41,
  "patientId": 12,
  "doctorId": 5,
  "appointmentDate": "2026-10-01",
  "startTime": "10:00",
  "endTime": "10:30",
  "status": "SCHEDULED",
  "cancellationReason": null,
  "consultationFeeSnapshot": 500.00
}
```

Note what the response shows but the request did **not** contain:

- `id` — generated by the database,
- `status` — set by the service (`SCHEDULED`),
- `consultationFeeSnapshot` — copied from the doctor's current fee by the service, so a
  client can neither discount nor inflate the price,
- the status history — written to `appointment_status_history` by the service, never
  submitted by a client.

Times are pinned to `"HH:mm"` in responses via `@JsonFormat`, so the format is a deliberate
part of the contract and not a Jackson accident. (Both `"10:00"` and `"10:00:00"` are
accepted as input.)

### Read an appointment

```http
GET /api/v1/appointments/41
```

`200 OK` — same body shape as the creation response.

### Cancel an appointment

```http
POST /api/v1/appointments/41/cancel
Content-Type: application/json

{ "cancellationReason": "Patient asked to reschedule" }
```

`200 OK`:

```json
{
  "id": 41,
  "patientId": 12,
  "doctorId": 5,
  "appointmentDate": "2026-10-01",
  "startTime": "10:00",
  "endTime": "10:30",
  "status": "CANCELLED",
  "cancellationReason": "Patient asked to reschedule",
  "consultationFeeSnapshot": 500.00
}
```

Cancellation returns the updated resource with `200 OK` (rather than `204 No Content`) so
the caller can see the new status and the recorded reason without a second request. The
cancellation reason is mandatory in the body — the database itself requires it
(`CHECK (status != 'CANCELLED' OR cancellation_reason IS NOT NULL)`).

## HTTP Status Codes

| Status | When it is returned |
|---|---|
| `201 Created` | an appointment was booked (with a `Location` header pointing at it) |
| `200 OK` | an appointment was read or cancelled successfully |
| `400 Bad Request` | the request itself is wrong: missing/invalid fields, `start >= end`, date in the past, malformed JSON, wrong path-variable type |
| `404 Not Found` | the request refers to a doctor, patient, or appointment that does not exist |
| `409 Conflict` | the request is valid but current data forbids it: inactive doctor/patient, window outside availability, slot already taken, illegal status change |

Only standard status codes are used — no custom codes.

## Validation

The request DTOs use **Jakarta Bean Validation** (`spring-boot-starter-validation`, added to
`pom.xml` in this step because Boot 4's `spring-boot-starter-webmvc` does not include it):

```java
public record CreateAppointmentRequest(
        @NotNull @Positive Long patientId,
        @NotNull @Positive Long doctorId,
        @NotNull @FutureOrPresent LocalDate appointmentDate,
        @NotNull LocalTime startTime,
        @NotNull LocalTime endTime
) { }

public record CancelAppointmentRequest(
        @NotBlank @Size(max = 255) String cancellationReason
) { }
```

`@Valid` on the controller's `@RequestBody` parameter triggers the checks. These annotations
only reject **structurally** wrong requests (missing or negative IDs, a date in the past, a
blank reason). The boundary between annotation validation and business validation is
deliberate:

| Lives in the DTO annotation | Stays in the service |
|---|---|
| field present, positive ID, date not in the past | doctor/patient exist and are active |
| reason present and ≤ 255 chars | time window inside availability, no overlapping booking, allowed status transitions |

If a rule needs to look at the database, it belongs to the service. The service keeps its
own defence-in-depth checks (for example the past-date check) so calling it without HTTP is
still safe.

## Exception Handling

`GlobalExceptionHandler` (`com.medbook.exception`) is a `@RestControllerAdvice`: one global
place that translates exceptions into HTTP responses. Controllers contain no `try/catch`.

| Exception | Status | Meaning |
|---|---|---|
| `DoctorNotFoundException` | 404 | no doctor row for that ID |
| `PatientNotFoundException` | 404 | no patient row for that ID |
| `AppointmentNotFoundException` | 404 | no appointment row for that ID |
| `DoctorInactiveException` | 409 | doctor exists but is deactivated |
| `PatientInactiveException` | 409 | patient exists but is deactivated |
| `DoctorUnavailableException` | 409 | window not covered by availability |
| `AppointmentConflictException` | 409 | slot already taken |
| `InvalidAppointmentStatusException` | 409 | illegal status transition |
| `IllegalArgumentException` (service checks) | 400 | invalid date/time values |
| `MethodArgumentNotValidException` (Bean Validation) | 400 | invalid request body fields |
| `HttpMessageNotReadableException` | 400 | missing body, malformed JSON, unparsable date/time |
| `MethodArgumentTypeMismatchException` | 400 | e.g. `GET /appointments/abc` |

Every one of them produces the same error shape:

```json
{
  "timestamp": "2026-09-21T11:42:07.315",
  "status": 409,
  "error": "Conflict",
  "message": "Doctor 5 already has an appointment overlapping 2026-10-01 10:30-11:30",
  "path": "/api/v1/appointments",
  "fieldErrors": []
}
```

- `message` is the message the service (or validation) wrote for that specific failure —
  never a stack trace, never SQL, never an internal class name.
- `fieldErrors` is filled only for request-body validation failures:

```json
"fieldErrors": [
  { "field": "patientId", "message": "patientId is required" }
]
```

Unmatched exception types are deliberately *not* swallowed: they fall through to Spring's
default `500` handling instead of being caught indiscriminately.

## Controller vs Service Responsibilities

| Controller owns | Service owns |
|---|---|
| URL paths and HTTP methods | who may book |
| JSON shape of requests/responses | which windows are bookable |
| `@Valid` + structural validation | which existing appointments block a slot |
| HTTP status for success | the transaction boundary and the row locks |
| mapping entities to DTOs | status transitions and the audit trail |
| choosing `Location` on creation | the consultation fee snapshot |

The complete `createAppointment` controller method is short by design — it contains no
decisions:

```java
@PostMapping
public ResponseEntity<AppointmentResponse> createAppointment(
        @Valid @RequestBody CreateAppointmentRequest request) {
    Appointment created = appointmentService.createAppointment(
            request.patientId(), request.doctorId(),
            request.appointmentDate(), request.startTime(), request.endTime());
    return ResponseEntity
            .created(URI.create(BASE_PATH + "/" + created.getId()))
            .body(AppointmentResponse.from(created));
}
```

## Security Boundary (Temporary Development State)

Authentication and authorization are **not** part of this step. The appointment endpoints
currently accept anonymous requests, and the request body itself carries `patientId` — which
is only acceptable during development.

This also means no fake identity is invented: the audit history column
`changed_by_user_id` stays `NULL` until the authentication step can identify the real
caller.

When security lands (later step), the plan is:

- `patientId` comes from the authenticated user, not from the request body,
- `changed_by_user_id` is populated from the authenticated user,
- role-based rules (patient cancels own appointments, admin/doctor see theirs) are added
  on top of these endpoints without changing the service's booking rules.

## Testing

`AppointmentControllerTest` runs MockMvc against the **full application context** with the
real service and the real MySQL database (`@SpringBootTest` + `@Transactional`, rolled back —
same approach as the existing repository and service tests; the service layer is not mocked
away). It verifies all 14 required behaviours: successful creation, validation failures,
404/409 mappings for every service exception, retrieval, cancellation (valid, blank reason,
too-long reason, unknown appointment, already cancelled), the error-response structure, and
JSON serialization/deserialization (including the pinned `HH:mm` time format).

## Known Limitations

- `created_at` / `updated_at` are not in the response: they are filled by MySQL and the
  entity mapping marks them `insertable = false`, so a just-created entity does not carry
  them (including them would mean `null` on POST but a value on GET). They will be added
  together with a mapping decision (e.g. Hibernate `@Generated`).
- `reason` / `notes` are not accepted yet: the service signature does not take them, and the
  controller must not write data behind the service's back. They arrive with a service
  signature extension.
- No doctor/patient listing endpoints yet (service has no listing methods).
- No pagination, no filtering, no Swagger/OpenAPI (no OpenAPI dependency is configured).
